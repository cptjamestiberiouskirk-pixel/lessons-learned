# Changelog

## Unreleased

- The playbook template's "The lessons check" now says to run it first in a session, before any other command, read-only ones included, with words for the task, and then before each of the steps it lists.
- A second hook, the lint hook (`hooks/lessons-lint.mjs`, the same file in both copies), runs after an edit: Edit, Write or MultiEdit in Claude Code, `apply_patch` in Codex. When the edit changes `LESSONS.md`, `PLAYBOOK.md` or a rule file that `--lint` reads, in a repo whose `PLAYBOOK.md` has "The lessons check", it tells the agent what `--lint` finds in that file, in at most 10 lines with errors first. When an Edit, MultiEdit or patch adds a lesson, it also names the open lessons and PLAYBOOK steps whose rules overlap the new one (`second-sighting` and `dup-rule`), so the agent can promote instead. It says nothing when it finds nothing, and never blocks. It imports the plugin's own `templates/lessons.mjs` into its process and calls it there, so it starts no program and never runs the repo's copy. `LESSONS_GATE=off` turns it off with the gate. In Codex it runs once trusted in `/hooks`, like the gate. The playbook template's "Limit:" paragraph says so.
- The playbook template's step 6 closes a lesson only when a test or a tool now enforces its whole rule, and its `closed:` reason names that test or tool. A code change alone no longer closes a lesson, and neither does a check that covers part of the rule. `--stale` is for finding Evidence to fix, not lessons to close, and its footer, the line past 50 lessons in `--section` and the section size warning say the same. The lessons template's Status line says `closed: <the test or tool that now enforces the whole rule>`. This repo's own step 6 changes the same way.
- The whole-file budget of `LESSONS.md` is 24,000 tokens, up from 16,000. Sessions read lessons through a lookup and `--section`, which keep their budgets of 2,000 and 1,500 tokens, so the file budget mostly warns about a whole-file read. A `Budget:` line still changes it. Its warning, and the one for `--all`, now say to raise the budget by its key (`Budget: lessons <tokens>`), not to shorten Evidence or close lessons, which keeps entries and makes the file larger.
- A section's lessons are the ones whose Status names it, so a section needs no `From:` line and `--check` no longer asks for one. A `From:` line a repo has may stay, and `--check` still checks that each name on it is a lesson promoted to that section, or it may be removed. Without Node, a search of `LESSONS.md` for `promoted to PLAYBOOK "<section>"` finds a section's lessons. The playbook template's steps 3, 5 and 6 no longer mention a `From:` line, except to remove a closed lesson from one that is left. This repo's `PLAYBOOK.md` drops its 13 `From:` lines, 575 words.
- `dev/lessons.mjs --section <number>` prints a PLAYBOOK section's steps, then the rules of the lessons promoted into it, so step 3 of the lessons check reads one section and its rules in one call, not the whole playbook. A lookup prints each section's number, and step 3 gives the number, never the section's name, which is repo text a shell could run. A person may give a name, in any case. A lookup that names a section points to `--section` on one line. Past the section budget (1,500 tokens) it says so.

- The playbook template's "The lessons check" step 5: lessons that share a rule become one short step that states it without copying them, and their rules give the details. Where a lesson's rule conflicts with the step, the step wins; a detail the step doesn't mention still applies. Step 3 reads the rules of a section's lessons and follows their details with its steps. Step 5's reviewer asks whether the step states the rule its lessons give, in short form, and nothing they don't say. Step 6 also removes the parts of a step that came only from a closed lesson.
- `--lint` reads a promoted lesson's rule too, not only its Evidence, since step 3 now has a session follow it. A file or flag it names that is gone is an error, as in an open lesson.
- `--lint` and `--stale` no longer read git's own names as file names: the line endings `git ls-files --eol` prints (`w/crlf`, `i/lf`, `w/mixed`) and a ref such as `origin/HEAD` or `refs/heads/main`. They made `--lint` fail on two repos that quote them. A name with an extension, such as `origin/notes.md`, is still a file name.
- `dev/lessons.mjs --lint --leads` (also `--doctor --leads`, or `--leads` alone) adds five rules that compare words. They are leads, so they are warnings, and plain `--lint` and `--doctor` don't run them. `dup-rule`: an open lesson's rule that a PLAYBOOK step may already cover, with the section and step number. `second-sighting`: two open lessons whose rules overlap, reported once on the newer one, with the closest older one named and the others counted. `promoted-drift`: a promoted lesson whose title and rule share no topic word and no span in backticks with its section's heading and steps, so it looks filed in the wrong section. This is not the plan's first version, which looked for a lesson's terms gone from its section: step 5 now makes a promoted step short, with the details in its lessons, so missing terms are by design. `quoted-tool-output`: Evidence that holds a stack frame, a Traceback, a line that starts with `Error:`, a quote over 200 characters, or a span in backticks over 200 characters. `unlabeled-claim`: an open lesson's Why that states a cause with no label and no word of what was tried. Each can be silenced in place. A silence for one of them is not reported as unused when the leads don't run. When there are more findings than `--lint` prints (100), the errors are chosen first, so many leads can't push an error out of the printed list.
- `dev/lessons.mjs --pairs` lists pairs of rules that share a topic and may pull in opposite directions, for a review to judge. It reads open and promoted lessons' rules, PLAYBOOK steps and the lines of rule files that read as rules. A promoted lesson is not paired with a step of its own section, since step 3 of "The lessons check" says that step wins. Two steps left as this release's playbook template wrote them are not paired either: they were written to agree, and paired 8 times in every repo. A repo with an older release's steps can still see pairs between them. Two lessons of one section are paired, since a detail the step doesn't mention still applies from each. Text shaped like a secret key is removed before a rule's words are read, so no part of it is printed. A pair shares two or more topic words, or a command in backticks, and has a cue: never against always, one at a time against at once, must against don't for the same thing, before against after the same thing, a word one forbids that the other says to do, two commands for one action, or a negation against a plain statement. The two weak cues, a word one forbids and a negation, count only for two texts that share more of their topic, or the same command, since common words made them fire on most pairs. It prints at most 40 pairs, strongest first, as `PAIR` lines, then a count line. `--pairs --json` prints one object. It compares at most 600 rules and steps, and says so when it stops there.
- `--lint` and `--doctor` report an open lesson that a lookup with any one of the topic words in step 1 of "The lessons check" leaves out, and a section with promoted lessons that no such lookup points to (`unreached`, a warning). Step 1 is read as Markdown reads it: a line numbered `1.` or `01.` and the lines after it, indented or not, up to a blank line or the next list item. A topic word is a span in backticks with no space, at least one letter or digit, and no `-` at its start, taken in lower case as a lookup takes it, so `node.js` and `c++` count. A lesson a word finds only past the lookup's cap of 50 items counts as left out, and the finding names that word. The check uses at most 20 topic words of at most 40 characters each, and says when it uses fewer than step 1 lists. Past a work limit (the lessons times the words, or the lessons' text times the words' length) it says so and checks nothing, and then a silence of it is not reported as unused. Like any finding, it can be silenced in place. The lint hook doesn't run it, since it would name every such lesson after each edit of `LESSONS.md`.

## 0.4.0 (2026-11-23)

The lessons gate, a hook in Claude Code and Codex that holds an edit or a commit until the lessons check is done, and `--lint` and `--doctor`, which find rules a session may not be able to follow.

- `dev/lessons.mjs --lint` finds rules a session may not be able to follow. It reports a file, command or flag that isn't in the repo, and evidence only one machine has. It reports an unsettled `INFERRED` or `HYPOTHESIZED` label and text that reads like an injected instruction. It reports the playbook's headings and steps out of order, and a lookup or section over its size budget.
- Each `--lint` finding has a rule ID and is an error or a warning. An error exits 1. A finding is silenced in place with `<!-- lint-ignore <rule>: <reason> -->`. `--doctor` adds a summary, `--all` lists the silenced findings, and `--json` prints one object for CI.
- A lookup over its budget says so on one line.
- `--lint` also reads the rule files (`CLAUDE.md`, `AGENTS.md`, or those a `Rule files:` line names), and the scripts its commands name, as text. The script still writes nothing and runs nothing.
- Another script can import `dev/lessons.mjs`: its functions take the repo root and return what they found, and the command line runs only when the file is started directly. The output of every existing mode is unchanged, except that a lookup over its budget ends with one more line.
- The Claude Code plugin has a hook, the lessons gate (`hooks/lessons-gate.mjs`). In a repo whose `PLAYBOOK.md` has "## The lessons check", it denies an edit, and a Bash or PowerShell command that runs `git commit` or `git push`, until Claude has written a visible `Lessons checked:` line in this turn, after its last commit or push to that repo, and before the call (a later call of the same message doesn't count). A turn that starts with a background task's notification (told by the record's origin fields, or by its text only in an older record that has none) carries on the turn before it. In the session's own repo, where `dev/lessons.mjs` is this release's or an earlier release's (0.2.0 to 0.3.1), a lookup with it is needed too. Repos already set up are gated as soon as the plugin is updated. `LESSONS_GATE=off` turns it off, and the deny message says so. It only reads, and lets the call through when it can't tell. SECURITY.md says how it reads commands and transcripts, and what gets past it.
- The Codex plugin ships the same lessons gate, the same file, with a `hooks/hooks.json` that runs it before each `apply_patch` call and each shell command, once you trust it (`/hooks` in the Codex CLI, Settings > Hooks in the desktop app). It reads Codex's rollout file: a `Lessons checked:` line counts in a visible message of the current turn, and an earlier commit or push is read from the commands that ran in it. A patch is gated by each file it adds, updates, deletes or moves to. A line counts only in its own turn. Codex starts the hook through the session's shell, and the hook's command runs the same in PowerShell 7, cmd and sh. Where the session's shell is Windows PowerShell 5.1, the hook lets every call through.
- Setup names a script from an earlier release by its version (it knows the fingerprints of 0.2.0 to 0.3.1), says what changed since, and asks before it replaces it. Since setup keeps the repo's `PLAYBOOK.md` and `LESSONS.md`, it then offers each part of the templates that differs, on its own. A script that is no release is still reported as "other version".
- Setup offers two checks that run `node dev/lessons.mjs --doctor` and fail only on an error: a CI step, and a pre-commit hook in the hook manager the repo uses (husky, lefthook, the pre-commit framework or a `core.hooksPath` folder), or a new `.githooks/pre-commit`. It adds each only if the user names it; a go-ahead for the plan doesn't take one. It never runs `git config core.hooksPath` or `chmod`, and gives the user those commands instead. These replace the offer of `--check` in CI. Setup's own check of its work runs `--doctor` too.
- Both setup skills write a `Lessons checked:` line before they build, and run a lookup once the script is in place, so the gate doesn't deny setup's own writes.
- The playbook template's "Limit:" line says what the hook checks, in Claude Code and in Codex, and what is still followed by hand.

## 0.3.1 (2026-11-18)

Fixes for the items 0.3.0's review left open.

- The copy command's real-path check compares the repo's real path exactly, and ignores only ASCII case in the rest of the path, on Windows and macOS, as `--stale` already did, and so also refuses a relative folder that climbs out of the repo with `..`. Before, it folded the whole path with `toLowerCase`, so a junction to a volume path could lead to a folder beside the repo whose name differs only in case: `REPO` in a folder marked case-sensitive, or `Kit` spelled with the Kelvin sign (U+212A), which NTFS keeps apart from `kit` in any folder. SECURITY.md no longer lists this as a known limit.
- `dev/lessons.mjs` reads `LESSONS.md`, `PLAYBOOK.md` and the files `--stale` searches through one handle, and checks that the handle is the file its look found (the same device and file ID, a regular file with one hard link, and as many bytes as it has). A file swapped between the look and the read (for a hard link to another file, another file renamed in, a FIFO, or a file given a second name), or grown after the handle's check, is not read: the script stops with "changed while it was read" for the two log files, and `--stale` says "not searched: it changed while it was read". A file that grows past the size limit after its look, and before the handle's check, is refused as over it ("is over 10485760 bytes"; for `--stale`, "not searched: over 1048576 bytes"). A symbolic link swapped in is refused too. Tried on Linux: for the two log files the open itself refuses it ("cannot read"; macOS's open takes the same flag), and `--stale` finds it in its real-path check ("not checked: a link on the way leads elsewhere"). A FIFO swapped in no longer makes the script wait for a writer forever on Linux and macOS. A folder on the way swapped for a junction after its look, back before the real-path check and in again before the open is still followed; SECURITY.md lists it as a known limit.
- `--stale` says "not checked: its real path cannot be read" when the system refuses a file's real path, where it said "no such file", which could lead someone to close a lesson whose file is still there.
- Both skills say to run the copy command as given, as its own `node` command for each file, and to tell the user when a run is refused rather than rewrite it. In a test run, a session whose loop of copies was refused ran the command from a script file instead, with the places it read its two paths from changed by hand.
- The playbook template's step 6 and the README say that `--stale` also names a file it didn't check or search, and why. The lessons template says the search text is on one line, since a search never matches across lines. SECURITY.md says that `--stale` searches untracked files too, such as `.env`.
- The 0.2.1 and 0.3.0 headings here give their release date.

Tests: a preload swaps the file right after the script's `lstat`, or grows it right after the `lstat` (past the cap) or the handle's `fstat`. `LESSONS.md` has a test for each kind of swap, and `--stale` one for a hard link. Each swap test fails on 0.3.0, and so does a test for the real-path error; the test that grows the file after the `fstat` can't run its preload on 0.3.0, which opens no handle, and fails instead on a script without the byte count. Each check of the read fails its own test when removed (the FIFO and symbolic link tests run on Linux and macOS), with two exceptions. No swap on one file system reaches the device check. The type check has no test of its own: only the FIFO test reaches it, where the system gives the FIFO the file's freed ID (ext4 does). The copy command has tests for the Kelvin sign and a case-sensitive folder, which fail on 0.3.0, and for two sibling names, which catch mutants of the new check that drop the separator after the repo's path or skip a character there. A test that fakes macOS for the case folding, in the copy and in `--stale`, fails on a mutant that folds case only on Windows. The growth test now takes Node's start off both runs and compares the full input with an eighth of it, so the script without the 200-unit limit fails it by about 3 times, where it failed by 1.3. `tests/links.mjs` counts `ENOTSUP`, which macOS gives for a hard link on FAT, as a refused link, so those tests skip there.

## 0.3.0 (2026-11-17)

Ideas taken from Google's Elephant-Goldfish Model, a plugin for designing and reviewing specs with agents: a check that docs still match the code, and review by a reader with no context.

- `node dev/lessons.mjs --stale` lists open and promoted lessons whose `Evidence` names a file in backticks (by its path from the repo root, holding a `/` or ending in an extension that starts with a letter) that is gone, or a `search "text"` after it that the file no longer holds. It is a lead for closing a lesson, not a verdict, and exits 0. It looks a name up under the repo root one part at a time, follows no link (it checks the file's real path too, since a junction to a volume path looks like a folder), reads only a regular file of at most 1 MB with one hard link, searches for at most 200 UTF-16 units of text (an emoji counts as two), never prints a file's text, and checks at most 100 names.
- The playbook template's step 6 says when to run it: after a change that deletes, moves or renames files, and before a release.
- The playbook template's step 5: before a promoted step goes in, a reviewer with no context (a subagent, where the tool can start one) reads only the step and its lessons, and checks that the step says what their rules say, no more and no less, and can be followed by someone who wasn't in the session. Without one, the session says so and asks the user to read the step.
- The lessons template says what makes a good entry: a rule someone else can follow, about this project, with evidence that can be checked later, and no open lesson that already covers it (if one does, promote that one). The format's `Evidence` line shows the form `--stale` reads: `` `path/from/root`, search "text" ``.
- Setup names the agents that read `AGENTS.md` (Cursor, Windsurf, OpenCode, GitHub Copilot) and offers the entry line in `GEMINI.md` for Gemini CLI, which reads that file unless its settings name `AGENTS.md`. It looks for rules kept in `GEMINI.md` too, and the path check covers it.
- The copy command works on an exFAT drive. There it failed every time with "is not the file this copy wrote", though the file was right: exFAT has no hard links, so the copy renames the file into place, and a rename on exFAT changes the file's ID, which the copy had read before the move. It now reads the ID of the file it still holds open after the move, and compares that with the target. Where a rename keeps the ID (NTFS, and Linux and macOS file systems), the check is the same as before.
- The README notes that a design-review plugin such as Elephant-Goldfish Model works beside this one: it writes specs under `docs/designs/` and review reports, not these files.

Tests: `tests/stale.test.mjs` covers `--stale`. Each of its guards (a link on the way, a junction to a volume path, one into a folder that differs from the repo's only by Unicode case, or only by case in a folder marked case-sensitive, or into a sibling whose name starts with the repo's, a repo opened through a link, a name in another case, a hard link, the size limit, the 200-unit search limit, and its cost for emoji, `..` in a name, the 100-name cap, the 50-lesson cap, the cut of a long name, skipping closed lessons) has a test that fails on a mutant with that guard removed. A growth test fails on a long search text without the limit. The copy command's tests have a preload that makes `fs` act as on exFAT, and the whole suite passes on an exFAT drive: a test that needs a hard link, a link to a folder or a freed name to stage its case skips where the file system has none.

Updating: the playbook and lessons template changes don't reach a repo set up with 0.2.1 or earlier on their own, since setup keeps an existing `PLAYBOOK.md` and `LESSONS.md`. Run setup again to replace the script (it reports "other version (not run)" and asks), and ask it to bring in steps 5 and 6 of "The lessons check" and the lessons header.
## 0.2.1 (2026-11-17)

Closes the two items left open by 0.2.0's review.

- Both setup skills bring a template in with one copy command that no longer relies on a create-only write, which isn't enough on Windows: through a dangling junction it creates an empty folder where the junction points, and in a probe it wrote through a dangling file symbolic link. It writes the template under a random name beside the target and gives it the target's name with a hard link, which fails on anything at that name and follows no link. If the hard link fails for any other reason (Codex's sandbox on Windows refuses one, and a FAT drive has none), it renames the file into place, which also writes through no link. It refuses a target given as an absolute path, and a source folder or target folder that is a link. It also refuses a target folder or relative source folder whose real path is not the one its path names, such as a junction to a volume path, which 0.2.0 took for a plain folder. At the end it checks that the target's folder is still the one it looked at, and that the target is the very file it wrote, with one name. It also refuses a source that isn't a plain file with one name, or that changes between its look and its read. A repo opened through a junction is accepted, where the 0.2.0 Codex copy refused it.
- The Claude Code skill no longer writes a template straight to its place with the Write tool. It writes it into a staging folder with a random name and brings it in with the same copy command as Codex, so a link made at the target after the path check isn't followed.
- In Claude Code, setup now runs a few more `node` commands (making and removing the staging folder, and one copy for each template), so it may ask for approval more often.
- `--check` keeps a message only for the 50 problems it prints, and counts the rest. A bad `From:` name past those 50 isn't made into a message at all. A `PLAYBOOK.md` with 465,000 bad `From:` names now runs in 40 MB of heap on Node 26, where 0.2.0 needed 256 MB (128 MB against 256 MB on Node 18).

## 0.2.0 (2026-11-16)

Codex support, and hardening against untrusted repo content.

- A Codex copy, `lessons-learned-codex`, with the skill `lessons-setup`. It shares the templates with the Claude Code plugin word for word, and sets up the same files, so a repo can be worked on from both. Install: `codex plugin marketplace add cptjamestiberiouskirk-pixel/lessons-learned`.
- `dev/lessons.mjs` treats `LESSONS.md` and `PLAYBOOK.md` as untrusted. It refuses a symbolic link, anything that isn't a regular file, a file with a second hard link and a file over 10 MB. It prints control and invisible characters (terminal escapes, bidirectional overrides, zero-width and Unicode tag characters) as `<U+XXXX>`, and `--check` reports them as bad. U+FE0E or U+FE0F right after an emoji, and a zero-width joiner after a non-ASCII character, pass where emoji and scripts use them; a run of them, or one elsewhere, is bad. Printed lines are cut at 2,000 characters, and a problem message names a title, section or `From:` name by its first 200; `--all` prints at most 50 lessons, a lookup at most 50 results with the playbook sections first, and `--check` at most 50 problems. Characters with ordinary uses (the zero-width non-joiner, direction marks, the soft hyphen) are spelled out but not counted as bad, unless the character after one is spelled out too. The checks run in time linear in the file's size.
- Setup doesn't run a repo's existing script until its fingerprint matches this version's, and runs a path check that stops on any symbolic link, junction or hard link before it reads or writes. Before its first `node` command it lists the repo root with a tool that isn't Node, and stops on any file named `node` or `node.` with an extension, which cmd on Windows would run in place of Node. The Codex copy copies a template only when nothing at all is at the target, a dangling link or junction included, and its folder isn't a link.
- Setup names the entry point for each tool: Claude Code reads `CLAUDE.md` and Codex reads `AGENTS.md`. When a repo has only one of them, setup asks whether the other tool is used too and offers the line there.
- The playbook template has a second section, "Checking your work", after the lessons check: before a change is called done or committed, run it the way it is used (in a local or test setup, asking before anything that changes real data), report each check that ran and each that didn't, make a test for a fix fail before the fix, never weaken a check to make it pass, and bring a check still failing after the number of fixes the user set (three if none) to the user. Adapted from the Claude Code team's post on verification.
- The lessons template says where entries go, below the format example, and `--check` reports an entry written inside a code block, which the script would never read.
- The playbook template says a rule never overrides the user or the agent's safety rules, that a rule asking for work outside the project is reported, not followed, and that entries record only what happened in the session and the user's words.
- Setup notes how it works next to a handoff plugin such as Trailmark: separate files, separate jobs, and a handoff names a lesson by title without repeating it.
- Setup brings in only what its plan lists: no tests or other files of its own. A project rule such as a lesson asking for a test with each new function is about the project's code, not the files setup adds.
- The playbook names a lesson in a handoff or memory note as `LESSONS.md "<title>"`, without copying its rule.
- SECURITY.md: how to report a problem, what runs with what rights, what is trusted, and the known limits.

Tests: `node --test` covers the script's handling of links, sizes, hidden characters, output caps and running time, the Codex copy's manifests and commands, and that the shared files match in both copies. Each security fix has a test that fails on the script before it. CI runs them on Linux, macOS and Windows, where the symbolic link tests run on the first two.

Updating: a repo set up with 0.1.0 has the older script. Run setup again, from either tool (`/lessons-learned:setup` in Claude Code, `lessons-setup` in Codex): it reports the script as "other version (not run)" and asks before replacing it. Setup keeps an existing `PLAYBOOK.md` as it is, so the playbook template's new trust rules (steps 3 and 4), the handoff-note wording and the "Checking your work" section don't reach an older repo on their own: compare its `PLAYBOOK.md` with `templates/PLAYBOOK.md`, and ask setup to bring those lines in.

## 0.1.0 (2026-11-16)

First version.

- `/lessons-learned:setup` adds a lessons log (`LESSONS.md`), a playbook (`PLAYBOOK.md`), a lookup and format-check script (`dev/lessons.mjs`) and an entry-point line in `CLAUDE.md` or `AGENTS.md` to a repo, and keeps them out of what the repo ships.
- Setup checks what the repo already has first. It changes nothing when everything is in place, adds only the missing parts, and asks before touching lessons kept under another name or a script that differs from this version.
- Setup shows its plan and waits for a go-ahead, then proves the format check catches broken entries and that the script came through intact.
