# Security

lessons-learned has no background process and no network access. It has two hooks, the same files in both copies, which only read (see below): the lessons gate, which runs before edits, commits and pushes, and the lint hook, which runs after an edit. Its setup skill (in Claude Code or Codex) writes three files into a repo and adds an entry line to `CLAUDE.md` or `AGENTS.md` and an exclusion to whatever the project ships with (`.gitattributes`, `package.json`, `.npmignore`), after you approve a plan that lists each change. From then on, sessions run `node dev/lessons.mjs` themselves as part of the lessons check, and they treat `LESSONS.md` and `PLAYBOOK.md` as instructions. This file says what that script can and can't do, what the setup trusts, and what's left to you.

## Reporting a problem

Report a security problem privately through GitHub: on the [repository](https://github.com/cptjamestiberiouskirk-pixel/lessons-learned), open the Security tab and choose **Report a vulnerability** (https://github.com/cptjamestiberiouskirk-pixel/lessons-learned/security/advisories/new).

Please don't open a public issue for anything that lets a repo, a web page or another program run code, read files or plant instructions through lessons-learned until a fix is out. Other bugs go in the repository's [issues](https://github.com/cptjamestiberiouskirk-pixel/lessons-learned/issues).

## What runs, and with what rights

| What | When | Rights |
|---|---|---|
| The setup skill | When you ask for it | The agent's own, under your Claude Code or Codex permission settings. It writes nothing until you approve its plan. |
| `dev/lessons.mjs` | When a session runs the lessons check, or you run it | Yours. It imports only Node's built-in modules, reads `LESSONS.md` and `PLAYBOOK.md` (with `--stale` the repo files their evidence names, and with `--lint` or `--doctor` the rule files, the files the text names and the scripts its commands name, and with `--pairs` the rule files), writes nothing, starts no programs and opens no network connections. |
| `node dev/lessons.mjs --doctor` in CI or a pre-commit hook | If you add one: setup offers each and adds it only if you name it. It never sets `core.hooksPath` or makes a hook file executable; it gives you those commands | The CI job's, or yours when you commit. It is the same script, doing the same reading. |
| The lessons gate, `hooks/lessons-gate.mjs`, in Codex | Before each `apply_patch` call and each shell command (`Bash` in the hook's input), once you trust the hook (`/hooks` in the Codex CLI, Settings > Hooks in the desktop app; both save it in `config.toml`) | Yours, as a Codex hook. It is the same file as in Claude Code, doing the same reading, with Codex's rollout file as the transcript. Codex runs a hook's command through the session's shell (`pwsh -NoProfile -Command`, `cmd /c` or `sh -c`), or with none through `%COMSPEC% /C` on Windows and `$SHELL -lc` elsewhere, so `hooks/hooks.json` runs a `node -e` launcher that imports the gate from `PLUGIN_ROOT`, and does nothing unless that is an absolute path that starts with a drive letter, or with `/` and a letter, digit, `.`, `_`, `~` or `-`. Its command holds no `$`, `%` or backtick, so PowerShell 7, cmd and sh read it the same, and each prints only the gate's answer, which Codex reads as JSON. Codex runs a hook in the session's folder, and cmd looks for `node` there before `PATH`, so a `node.cmd` or `node.bat` in a repo would run in place of Node. The command's first step, `set NoDefaultCurrentDirectoryInExePath=1&&`, turns that look off for cmd (tried on Windows 11 with a planted `node.cmd`: without it the planted file ran, with it Node did). PowerShell 7 and sh run it as a harmless `set` and then run Node; neither looks for a program in the current folder (tried in pwsh 7 and Git for Windows' sh with a planted `node.cmd`, `node.bat`, `node.ps1` and `node`, and in bash and dash). Windows PowerShell 5.1 can't read `&&`, so if it is the session's shell the hook errs and lets every call through. Codex stops it after 10 seconds, and lets the call through when it errs or times out (from Codex 0.171's source, `hooks/src/engine/command_runner.rs`, and its hook docs; not tried in a live run). |
| The lessons gate, `hooks/lessons-gate.mjs`, in Claude Code | Before each Edit, Write, MultiEdit and NotebookEdit call, and each Bash and PowerShell call, while the plugin is installed | Yours, as a Claude Code hook. It imports only Node's `fs`, `path` and `crypto`, opens files only to read them, starts no programs and opens no network connections. It reads the target repo's `PLAYBOOK.md`, its `dev/lessons.mjs` (to hash it) and the session's transcript. It is started as `node` with the script's path as an argument, with no shell, and Claude Code stops it after 10 seconds (the `timeout` in `hooks/hooks.json`). Its work grows linearly with the transcript it reads, the commands in it and the text it searches for the line: each of those has a test that times a full input against a quarter of it, past the time of the same call on the smallest input, and failed every run against a slower version of that part (5 runs each in review round 3, and 3 each after round 4 changed what the fixed cost is). It skips a path over 4,096 characters or 512 names. A call it takes longer than 10 seconds on is let through, as Claude Code doesn't block on a hook that times out (from Claude Code's hook docs; not tried in a live run). |
| The lint hook, `hooks/lessons-lint.mjs`, in Claude Code and Codex | After each Edit, Write and MultiEdit call in Claude Code while the plugin is installed, and after each `apply_patch` call in Codex once you trust the hook | Yours, as a hook. It imports Node's `fs` and `path`, and this plugin's own `templates/lessons.mjs` by its path beside the hook, never the repo's `dev/lessons.mjs`. That script imports only Node's built-in modules and runs in the hook's own process, so the hook starts no programs and opens no network connections. It reads the repo's files only through that script, as `--lint` reads them. In any repo with a `LESSONS.md`, it reads both files through that script after any edit, to learn whether `PLAYBOOK.md` has the lessons check and which rule files `--lint` reads. It reports only in a repo with that section, and only on an edit to `LESSONS.md`, `PLAYBOOK.md` or one of those rule files. Claude Code starts it as `node` with its path as an argument, with no shell; Codex through the same launcher as the gate, from `PLUGIN_ROOT`. Each tool stops it after 10 seconds. It never blocks a call: on any error it prints nothing. |

## What it trusts, and what it doesn't

| Input | Treated as | What is done about it |
|---|---|---|
| A file named `node`, or `node.` with any extension (`node.exe`, `node.cmd`, `node.js` and so on), in the repo root | Code that cmd on Windows would run in place of Node | Before its first `node` command, setup lists the repo root with a tool that isn't Node, and stops if one is there, whatever its case. |
| A `dev/lessons.mjs` already in the repo | Untrusted code | Setup hashes it first (line endings ignored) and runs it only if the hash matches this release's template. Otherwise it reports "other version (not run)" and asks. |
| Files setup reads (`CLAUDE.md`, `AGENTS.md`, an existing log) | Data | The skill says to quote any instruction found in them to the user, not follow it. |
| A symbolic link, junction or hard link at a path setup writes (`LESSONS.md`, `PLAYBOOK.md`, `dev`, the entry-point files, and any other path in the plan) | A way to write outside the repo | Setup runs a path check before reading and again before writing, and stops on any link. Both copies then bring the three templates in with one copy command. It refuses anything already at the target, a dangling link or junction included, a target given as an absolute path, a target whose folder is a link or whose real path is not the repo's real path followed by the folder's path (a junction to a `Volume{...}` path is not a link to `lstat`, so the copy compares real paths too, which also refuses a path that climbs out with `..`: the repo's real path exactly, then the rest with only ASCII case ignored, on Windows and macOS), and a source that isn't a plain file with one name, or that changes between its look and its read. It writes the file under a random name beside the target and gives it the target's name with a hard link, which fails on anything at that name and never follows a link there. If the hard link fails for any other reason (Codex's sandbox on Windows refuses one, and an exFAT or FAT drive has none), it renames the file into place, which replaces the name itself and also writes through no link. It refuses a source folder that is a link, and a relative one whose real path is not the repo's real path followed by its path, compared the same way. It looks at the source and its folder again after the read. Last, it checks that the target's folder is still the one it looked at, and that the target is the very file it wrote, with one name, and fails if not. It reads that file's ID from the handle it still holds, after the move, since a rename on exFAT changes a file's ID. The Claude Code copy first writes each template with the Write tool into a staging folder with a random name, made fresh in the repo. |
| `LESSONS.md` and `PLAYBOOK.md` when the script reads them | Untrusted text | The script reads only a regular file of at most 10 MB in the repo root, with one hard link. It refuses a symbolic link and a file with a second hard link, so a repo can't make it print a file from outside. It finds the repo root from the path it was started with, so a `dev` folder that is a link to another project doesn't move the root there. Its checks run in time linear in the file's size. |
| File names in the `Evidence` field, read by `--stale`, and file names in the text, rule files and scripts, read by `--lint` | A way to make the script read files outside the repo, or a huge or special one | Only a plain relative path of ASCII letters, digits, `.`, `_`, `-` and `/` that holds a `/` or ends in an extension that starts with a letter, with no empty, `.` or `..` part, counts as a file name, so an absolute path or one that climbs out of the repo is never looked up. It is looked up under the repo root one part at a time, and a symbolic link or junction on the way is not followed, as long as it stays in place (see the known limits). A junction to a volume path looks like a plain folder, so the file's real path must also start with the repo's real path, exactly, and go on with the name, with only ASCII case ignored on Windows and macOS. Only a regular file of at most 1 MB with one hard link is read, through one handle that must be the file the look found (the same device and file ID, a regular file with one hard link, checked after the open, and exactly as many bytes as the handle says it has), so a file swapped after the look is not read. Where the system allows, the open follows no symbolic link and doesn't wait on a FIFO. It is searched for the quoted text, of at most 200 UTF-16 units, where an emoji counts as two (a longer search could take minutes). The file's text is never printed, only whether it holds that text. At most 100 names are checked, then a count. `--lint` and `--doctor` look names up the same way, and read with the same checks. They read at most 20 rule files: `CLAUDE.md` and `AGENTS.md` at the root, or the files the `Rule files:` setting names. They read a script that a command in backticks names (`.mjs`, `.js`, `.cjs` or `.ps1`) as text, to see whether it knows a flag. The script is never run. At most 400 names and flags are looked up, then a count. A script's text is never printed. A rule file's text is printed only by `--pairs`, and only the topic words and the spans in backticks that two rules share, and for two commands for one action, the first word of each command. Each line is made safe as any other line is. Text shaped like a secret key is removed before a rule's words are read, a private key from its BEGIN line to its END line (or to the end of the text), and so is a key the line limit cuts short. So no part of one becomes a topic word that `--pairs` or a lead prints. `--pairs` reads the rule files the same way `--lint` does. |
| Control and invisible characters in the two files (terminal escape codes, bidirectional overrides, zero-width characters, Unicode tag characters, every other default-ignorable code point) | A way to hide text from a person but not from the agent, or to drive the terminal | The script prints each one as `<U+XXXX>`, and `--check` reports the line as bad. Tab passes through. So do U+FE0E or U+FE0F right after an emoji (digits, `#` and `*` count, for keycaps), and a zero-width joiner (U+200D) after a non-ASCII character with no other such character after it, since emoji and some scripts need them there. Before a space or the end of a line, a joiner passes only after a letter or mark, as in a word-final form. Anywhere else they are spelled out and bad. The zero-width non-joiner, the direction marks and the soft hyphen are spelled out but not counted as bad, since Persian, Hebrew, Arabic and pasted text use them, unless the character after one is spelled out too. |
| Very long lines, many lessons or many problems | A way to flood the session | Each printed line is cut at 2,000 characters, and a problem message names a title, section or `From:` name by its first 200. A lookup prints at most 50 results (the playbook sections first, so open lessons never push them out, then open lessons), `--all` at most 50 lessons, `--section` at most 300 lines of the section and 50 lessons, and `--check` at most 50 problems, then a count. `--lint` prints at most 100 findings, each cut like any line, and a finding about text shaped like a secret key never prints the text. It keeps at most 20,000 findings and still counts the errors past that, and its content rules read at most 4,000 characters of a line, so their cost stays linear in the file's size. `--pairs` prints at most 40 pairs, each naming at most 8 shared words and 8 spans. It compares at most 600 rules and steps, reads at most 4,000 characters of each and keeps at most 128 words of each, and compares two only when they share a topic word or a command, so its cost stays bounded. |
| The rules in `LESSONS.md` and `PLAYBOOK.md` | Repo instructions, like `CLAUDE.md` | The playbook says a rule never overrides the user or the agent's safety rules, and a rule asking for work outside the project (network, credentials, files outside the repo) is reported, not followed. Entries record what happened in the session and the user's words, never text copied from tool output or web pages. |
| A section's name in `PLAYBOOK.md`, which a session could put in a command | A way to run code: a name such as `$(...)` in double quotes runs in the shell before `node` starts, and `--check` accepts such a name | "The lessons check" step 3 runs `--section <number>`, with the number the lookup printed, never the section's name. The lookup prints the number of each section it names, and its pointer line says to give the number. A Status that names no section of `PLAYBOOK.md` gets no number, only a pointer to `--check`. No printed line asks for a name. `--section` reads a value of digits only as a number. A person may still give a name they typed. |
| A repo's `PLAYBOOK.md` and `dev/lessons.mjs`, read by the lessons gate | Untrusted files that decide whether, and how strictly, the gate acts | The gate acts only in a repo whose `PLAYBOOK.md` has a line that is exactly `## The lessons check` (after a BOM, if there is one). It finds the repo from the edited file's real path, or from the folder a commit or push runs in, and stops at the first `.git` above it. It reads each file as the script does: no link on the way, a regular file with one hard link, at most 1 MB, a real path that is the repo's real path followed by the name, and one handle that must be the file its look found. It skips UNC and `\\?\` paths. It never runs the repo's script: it hashes it, and asks for a lookup only in the session's own repo, when the hash matches this release's template or an earlier release's (0.2.0 to 0.3.1); only a `node` command that runs that repo's own `dev/lessons.mjs` with at least one topic word counts as one (`--check`, `--stale` or `--all` alone don't, and a `--section` name is not a topic word). Edits under `.git/`, and under `.claude/` other than the `settings*.json` files at its top (which could turn the gate off), are not gated; on Windows a name such as `settings.json.` or `settings.json::$DATA` counts as the settings file it opens. That leaves `.claude/CLAUDE.md` and `.claude/rules/` ungated, though Claude Code reads them as instructions, as it does the gated `CLAUDE.md` in the root. Its deny message is fixed text, so a repo can't put words in it. |
| A Bash or PowerShell command, read by the lessons gate | Text to find each `git commit` and `git push` in, and the folder it runs in | The gate reads a call whose text may name git: `git` in any case (Windows and macOS run git for `GIT`), with quotes, escapes, a line join or a carriage return between its letters, or with an escape that makes a letter (bash's `$'\x67it'`, pwsh's `` `u{67} ``). The command is split as its shell would split it: quotes and escapes (bash's `$'...'` and `$"..."` too; bash's `$'...'` is decoded as bash decodes it, `\n`, `\x0a` and `\cJ` included, and pwsh's `` `n ``, `` `r `` and `` `u{ } `` are the characters they make), spaces (bash reads a space or a tab, and pwsh also a vertical tab, a form feed, U+0085, U+00A0 and the other Unicode spaces, but not U+FEFF), separators, redirections, comments (PowerShell's `<# #>` too), PowerShell script blocks (`try { }`, `ForEach-Object { }`), here-doc and here-string bodies (text, not commands; a here-doc's tag is the word after `<<` as bash reads it, quotes and all, so `cat <<E+F` ends at a line `E+F`; a tag whose quote or `$( )` isn't closed on its line starts none; a `<<` in quotes, in a `$(( ))` or `$[ ]` that ends on its line, or in a comment starts none, while one in a `$( )` inside double quotes, as in `git commit -m "$(cat <<'EOF' ...`, does; an `@'` in a PowerShell quote or comment opened on its own line starts none, and a `$( )` inside PowerShell double quotes is code, so its quotes don't end the string), `$( )` and backtick substitutions (a `$( )` is read by its shell's rules: inside double quotes it is code, so a quoted string in it, and a `$( )` in that, nest; in it a `#` that starts a word is a comment to the line's end, though not in Bash's `$(( ))`, and so is PowerShell's `<# #>`; Bash's `$'...'` has its `\` escapes; and in PowerShell a `$( )` inside double quotes ends at the `)` that balances its parentheses, with each `""` or `` `" `` in it read as one `"`. Each command is read a second time with a `$( )` ended by its quotes alone, as the gate read it before, and a commit or push that either reading finds counts. The known limits list forms that both readings miss), and `bash -c`, `sh -c`, `pwsh -Command`, `cmd /c` and `cmd //c` inside it. That holds among a command's arguments. Where pwsh reads an expression, as after `=` or a comma or at a statement's start, it is a space after any word, and the gate doesn't tell the two apart, so it reads a word it can't place each way (below). In pwsh a quoted string or a `$( )` that starts a word ends it unless an index or a member follows, so `git "push"x` runs `git push x`, and a `#` right after one starts a comment. The gate can't tell which bash runs a command, or how pwsh reads every word, so a command that holds a carriage return, a backtick and a line feed, or an escape that can make one (bash's `$'...'`, pwsh's `` `r ``, `` `n `` and `` `u{ } ``), is also read once for each pair of ways that can read it otherwise: bash on Linux's or Git Bash's, with each PowerShell word the gate can't place read as one the backtick is inside, or as one it ends. A commit or push that any reading finds counts. Before `git` it passes over variable assignments (PowerShell's `$out = `, `$a, $b = ` and `$a=$b=` too, though not every PowerShell form: see the known limits), shell keywords (`then`, `do`, `time`) and wrappers (`env`, `sudo`, `doas`, `command`, `builtin`, `exec`, `nohup`, `nice`, `stdbuf`, `timeout`, `xargs`, `wsl`) with their options, short or long; a long option it doesn't list that takes its value as the next word hides the command after it, and so do `env -S` and `env --split-string`. The folder is git's `-C`, `--work-tree` or `--git-dir`, else `env -C DIR`, `env --chdir DIR` or `env --chdir=DIR`, or `wsl --cd`, for that command, else the last `cd`, `Set-Location` or `pushd` before it, else the folder the call was made in: for an earlier call, the `cwd` in its own transcript record; for the current one, the payload's. A command in a `$( )` or backticks is judged in the folder the call was made in, not one an earlier `cd` moved to. `popd` goes back; `cd -` goes back to the folder before the last `cd` in the same command, and stays put when there was none; a `cd` inside a bash `( )` subshell ends with it, and a `case` pattern's `)` closes none (in PowerShell `( )` is no subshell). A dry run (`--dry-run`, `push -n`) is not a commit or push; `commit -n` skips hooks and is a commit. |

## Known limits

- **The rules are instructions.** Anyone who can change `LESSONS.md` or `PLAYBOOK.md` can change what every session is told to do, as with `CLAUDE.md` or `AGENTS.md`. The playbook's own trust rule limits what a rule can ask for, but it is followed by the model, not enforced by a tool. Review changes to these files like code; setup's report suggests a `CODEOWNERS` entry.
- **The lessons check is mostly followed by hand.** The script checks the files' format and, with `--stale`, whether the files their evidence names are still there. `--lint` finds rules that name what isn't there or read like an injected instruction, by pattern: it can't tell whether a rule is right, and text written to slip past its patterns will. In Claude Code and Codex, the lessons gate denies an edit, commit or push until the session has written a `Lessons checked:` line in that turn, after its last commit or push to that repo (and run a lookup, where the session's repo has this release's script or an earlier release's). It is a nudge, not an enforcement boundary. It checks that a line was written, not that it names the right lessons, and it doesn't check test runs. These get past it:
  - a write through the shell (`sed -i`, `Set-Content`, `node -e`), an MCP tool or any other tool;
  - a commit or push it can't see in the command: a git alias (`git ci`), a command built at run time (`eval`, `Invoke-Expression`, `$cmd`, or a variable inside the word, as in `g${9}it push`), an empty variable or substitution before git's subcommand, which the shell drops (`git $x push` with `$x` empty, `git $(true) push`), one inside a script or a program that runs git (`bash commit-as.sh`, the commonest case in real sessions, or `npm run release`, `gh`), and one nested more than four levels deep, where each `bash -c`, `pwsh -Command`, `cmd /c`, `$( )` or backtick substitution is a level;
  - a commit or push in a form the command reader gets wrong (review round 4 found none of these in the real sessions it replayed). The first twenty are missed, and the last two are judged in the wrong folder. Two forms in one command can also be missed together though each is caught alone, so one of these can hide a commit or push that the gate's other rules would find: `x=$(echo ${y:- #}); git push` and `x=$(echo $'\''); git push` are denied, and `x=$(echo ${y:- #} $'\''); git push` is not; nor is `x="$(echo a # it's`, then `)"; a=$(echo ${y:- #}); git push`:
    - in bash, a `$(( ))` or `$[ ]` that goes on to the next line, or a `$'...'` with an escaped quote, before a here-doc: the here-doc scanner reads `<<` there as an opener, or a quote as open, so a commit after it is read as text (`x=$((1 +`, then `2 << 3))`, then `git commit -m x`; `echo $'it\'s'`, then a here-doc whose body holds `Bob's`, then `git commit -m x`);
    - in bash, a `#` inside `(( ))`, which the gate reads as a comment to the line's end, at the top of a command or in a `$( )` (`(( 1 # 2 )); git push`: bash reports an error for the `#` and runs the push);
    - in bash, a `$( )` inside a `$(( ))` or `(( ))` that is inside double quotes: the gate reads a `#` in it as text, not a comment, so a `'` after the `#` opens a quote (`n="$(( 1 + $(echo 1 # it's`, then `) ))"`, then `git push`);
    - in bash, `$$` right before a quote, or before a `(` in double quotes, which bash reads as the variable `$$` and a plain quote or text, and the gate as a `$'...'` with `\` escapes or the start of a `$( )` (`echo $$'\'; git push`; `x="$$("`, then `git push`, then `# )"`);
    - in bash, a `${ }` that holds a `#`, a `)` or double quotes, which the gate doesn't read as one piece (`echo ${y:- #}; git push`; `echo "${y:-"it's"}"`, then `git push`);
    - in bash, backticks inside a `$( )` in double quotes, or inside a double-quoted string in a `$( )`, whose `)`, `#` or quotes the gate reads as the `$( )`'s own (`` x="$(echo `echo a # )`)" ``, then `git push`; `` x=$(echo "`echo ")"`"); git push ``);
    - in bash, a `case` pattern with no `(` in a `$( )` in double quotes, whose `)` the gate reads as the end of the `$( )` (`x="$(case a in a) echo "it's";; esac)"`, then `git push`);
    - a `$( )` or backticks in a here-doc body or a PowerShell `@" "@` body, which the shell runs and the gate reads as text (`cat <<EOF`, then `$(git push)`, then `EOF`);
    - `env -S` and `env --split-string`, which run a command given as one word (`env -S "git push"`);
    - in bash, brace expansion, which makes words of one word, so `git` can come from one that doesn't read `git` (`{git,} push`, `{git,push}`), and a pattern such as `?` or `[h-j]` in the command's name, which bash replaces with the files it matches (`/usr/bin/g?t push`);
    - in PowerShell, `$x =git push`, `$a,$b=git push`, `$a ,$b = git push`, an index or a member as the target with its `=` joined to it (`$x[0]= git push`), and a typed target such as `[string]$x = git push`;
    - in PowerShell, a `#` right after an index or a member, or right after a value where pwsh reads an expression, such as after `=` or at a statement's start, which pwsh reads as a comment and the gate as text (`echo $x[0]#'`, then `git push`; `$m = $x#'`, then `git push`). After a quoted string or a `$( )` that starts a word, the gate reads it as pwsh does;
    - in PowerShell, a `<#` inside a word, which pwsh reads as part of the word and the gate as the start of a comment (`echo x<# ; git push #>`);
    - in PowerShell, `$$(` in double quotes, which pwsh reads as the variable `$$` and text, and the gate as the start of a `$( )` (`$m = "$$(" ; git push`);
    - in PowerShell, a `${ }` variable name that holds a `$(` in double quotes, or a `)` in a `$( )`, which the gate reads as a `$( )` that never ends, or as the end of one (`$m = "${a$(}"`, then `git push`; `$m = $(${a)'}); git push`);
    - in PowerShell, typographic quotes such as U+201C and U+201D, which pwsh reads as double quotes and the gate as text, so a `'` inside them opens a quote (`$m = `, then `it's` between typographic quotes, then `git push`);
    - in PowerShell, a double quote or a `<# #>` comment opened on an earlier line, which the here-string check doesn't see (`Write-Host "start`, then `note @'`, then `"`, then `git push`, then `'@ end'`: PowerShell runs the push, and the gate reads it as a here-string's body; or `$m = $($x <# a`, then `#>) + @'`, then a body holding `it's`, then `'@`, then `git push`);
    - in bash, a here-doc whose command goes on past its line. bash starts the body after the line the command ends on, and the gate on the next line, so a commit or push between them is read as text (`cat <<E \`, then `; git push`, then `E`). The command goes on past a `\` at the line's end, which can also join the tag (`cat <<E\`, then `F`, then `EF`, then `git push`, then `E`), and past a quote, a `$( )` or backticks open at the line's end (`cat <<E "`, then `"; git push`, then `E`). Under a tag with no quote, a `\` at the end of a body line joins it to the next, so `E\` and then an empty line close `cat <<E`. And after a line join, a `#` that goes on a word starts no comment (`echo a\`, then `#'`, then `cat <<E`, then `'; git push`, then `E`);
    - in PowerShell, a backtick and a line end after a parameter the gate doesn't read as one: after a comma, or with a character other than a letter, a digit, `_`, `?`, `$` or `-` in its name. pwsh reads a parameter there, so the line ends and the next line is a command (`echo a,-a` or `echo -a=`, a backtick and a line feed, then `git push`);
    - in PowerShell, two words in one command that the gate can't place before a backtick and a line end, where pwsh reads one as a plain argument, so the line end is part of it, and the other as an expression, as after `=`, so the backtick and the line end are a space. Each reading takes all such words one way, so neither finds the push pwsh runs (`echo a`, a backtick and a line feed, then `#'`, then `echo "`, then `'`, then `$m = $x`, a backtick and a line feed, then `#'`, then `git push`, then `#'`, then `#"`);
    - `env -C"DIR"` with the folder joined to the option, and `sudo -D DIR` or `sudo --chdir DIR`: the folder is not followed (`env -C"/path/to/repo" git commit -m x`);
    - a commit or push inside a `$( )` or backticks after a `cd` in the same command (`cd /path/to/repo && out=$(git push)`), judged in the folder the call was made in;
  - a subagent's calls;
  - any call where it errs, or finds a turn start whose prompt ID isn't the payload's;
  - a call whose own record isn't in the transcript within 1.3 seconds, in a transcript with no user or assistant record of the session (its `sessionId`). All 20,192 user and assistant records in one session's transcript carry it. A forked session's transcript can start with only its parent's records, under the parent's `sessionId`, and there such a call passes. If Claude Code stopped writing `sessionId`, a late record would get the call through, as it did before this check;
  - a call whose hook the tool's timeout ends before the gate's own deadline does. Claude Code ends a hook at its 10 second timeout and then runs the call: in 2.1.332, with a gate still reading at 10 seconds, a `git push` it would have denied ran. So the gate stops reading 6 seconds after Node starts and denies the call. The timeout comes first only when Node's start, or work the gate doesn't time (reading the transcript, or one stretch of a command between two looks at the clock), takes the other 4 seconds. Codex does the same: in 0.172.0, a hook given a 5 second timeout that would have denied a `git push` after 15 seconds was ended, and Codex ran the push (git started, then couldn't reach the run's local remote). Its hooks.json gives the gate 10 seconds, as Claude Code's does, so the same 6 second deadline covers it.

  A line written before a background task's notification still counts after it, and after any chain of them that fits in the 32 MB the gate reads, until the next commit or push. An older transcript record with no `turnOrigin` or `origin` field is taken as a notification when its text starts with `<task-notification>`.

  Where it can't find the line it denies, so a change in how Claude Code writes the transcript that hides text blocks from it would deny every gated call until it is turned off. In Claude Code it also denies a call whose own record it can't find in a transcript of this session within 1.3 seconds. Claude Code can write the record later (in one test, 5.9 seconds after the record's own time, for the first of two calls in a message), so such a call is denied and has to be retried, as the only call of the next reply. A change in how Claude Code writes calls that puts them in a new record type, or in a user record, would deny every gated call there in the same way, until the gate is turned off; the deny says to tell the user when it keeps coming back. It also denies each gated call of a turn it can't read within 6 seconds, until the next turn; that deny also says to tell the user when it keeps coming back. On one Windows machine that took 2.5 MB of commands nested four deep in `bash -c "$(`, with a carriage return at each line end (2 MB passed, in 4.8 seconds), or 6 MB with line feeds alone (5 MB passed, in 5.4 seconds). `LESSONS_GATE_DEADLINE_MS` in its environment can lower the 6 seconds, never raise them. `LESSONS_GATE=off` in its environment turns it off, and a repo's or your own Claude Code settings can set that through `env`; the deny message names this switch.

  In Codex these get past it too:
  - an `apply_patch` sent through the shell, as a here-doc: Codex reports it as a shell command, so the files it names are not gated;
  - the time before you trust the hook, and a Codex with hooks turned off;
  - outside Windows, a command in a shell other than sh, since the gate reads it as sh (zsh and fish split some words differently);
  - on Windows, a command run in a shell other than PowerShell, Codex's default there, since the hook's input doesn't say which shell runs it (all 13,072 commands in the local Codex sessions this was checked on ran in `pwsh`).

  In Codex a line counts only in its own turn. A turn that a scheduled heartbeat, a goal or another Codex trigger starts needs its own line: Codex has no counterpart to the background notification that carries a Claude Code turn on. `LESSONS_GATE=off` turns it off when it is in the environment Codex runs its hooks with (not tried in a live run). The facts about Codex above are from Codex 0.171's source and docs and from the hook input of real Codex sessions; no live Codex run has tried the gate.
- **The gate's `node` is found on `PATH`.** The hook starts `node` with no shell. Tried with Claude Code 2.1.330 on Windows 11: with a `node.exe` that can't run in the root of the repo the session was started in, the gate still ran the Node on `PATH` and denied the call. Other versions were not tried. A `PATH` that lists the repo's folder is still outside what this plugin can check; see "Node runs the script" below.
- **The path check and the write are two steps.** Something on the machine that swaps a file or folder for a link between them would not be caught everywhere. For the three template files, the copy command closes it at the file's own name: anything made there after the check makes the hard link fail, and nothing is written where a link points. Where it falls back to a rename, a link to a file made there is replaced, and so is a plain file made there in that instant; a junction made there makes the rename fail. A folder swapped for a link before the write would still be followed: `dev` in the instant between the copy's check of it and the write, and in the Claude Code copy the staging folder at any time between its creation and the Write tool's writes into it, which span several tool calls. The copy looks at the target's folder again at the end and fails if it changed, but by then the file is written where the link led, and under the rename fallback it may have replaced a file there. The copy checks the staging folder and the staged file again after its read, and at the target's folder at the end, so a swap that stays in place is caught. A process that swaps a folder back just before each look, and again just after it, is not: every look sees what it expects, and no look by path can close that. Later edits (topic words, the entry line, the exclusion) keep the gap. A create-only write alone isn't enough on Windows: tried on Windows 11, a dangling junction made it create an empty folder where the junction pointed, and in a probe it followed a dangling file symbolic link and wrote where it pointed.
- **`--stale` and `--lint` look a name up by path.** A process on the machine that swaps a folder on the way for a junction right after the script's look at it, back before the real-path check, and in again before the open, makes `--stale` open a file outside the repo and report whether it holds the text. The open checks the file it gets against the look, but the look went through the same junction. No look by path can close that: Node has no way to open a file relative to a folder it holds open.
- **`--stale` searches any file in the repo.** That includes untracked files such as `.env` or `.git/config`. An entry planted with `search "text"` learns whether such a file holds that text: one yes or no per name, and only if the leads reach someone who can see them. The file's text is never printed.
- **Some real text fails `--check`.** The England, Scotland and Wales flag emoji are built from tag characters, and some Japanese ideographs take a variation selector from U+E0100 up. Other text that fails: the selectors U+FE00 to U+FE0D (some math symbols and CJK forms), Mongolian free variation selectors and the vowel separator U+180E, the combining grapheme joiner in Hebrew, U+FE0E or U+FE0F after a character that isn't an emoji, the zero-width space that Thai, Lao, Khmer and Burmese text uses between words, the word joiner U+2060, the Hangul fillers, the Arabic end of ayah U+06DD and number signs U+0600 to U+0605, and a joiner after a space that shows an Arabic letter's form alone. All of these fail `--check`, since the same characters can hide text. The lookup still prints them, spelled out.
- **Where these characters are allowed, they can still carry data.** An emoji can be followed by nothing, a selector, a joiner or both, about 2.6 bits; another non-ASCII character by a joiner or not, 1 bit. Any gap between two characters, in ASCII text too, can hold one direction mark, non-joiner or soft hyphen, or none, about 2.6 bits. Those last are spelled out when printed, but `--check` passes them. It is a code a program would have to decode, not readable text like the tag characters that `--check` rejects.
- **After setup, the script is repo code.** Each session runs whatever `dev/lessons.mjs` the repo holds. Setup checks its fingerprint once; a later change to it is a code change like any other, and deserves the same review.
- **Node runs the script.** `node` is found on `PATH`, and on Windows cmd looks in the current folder first. Setup's listing catches a `node` file in the repo root at setup time, but not one added later. On Windows, setting the user environment variable `NoDefaultCurrentDirectoryInExePath` to `1` turns that lookup off for every program. Tried on Windows 11: in a folder holding a `node.js`, cmd ran the real Node with the variable set, and without it handed `node` to that file, which `.js` opens with Windows Script Host. A repo that puts its own folder first on your `PATH` is outside what this plugin can check.
- **Other plugins.** A handoff or memory plugin such as Trailmark keeps its own notes and runs its own hooks. lessons-learned doesn't read or write them, and its security is that plugin's own.
