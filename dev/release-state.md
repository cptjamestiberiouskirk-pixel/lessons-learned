# Release state

Where each release's review stands: the review rounds run, and what was found and left for later. Each deferred item is `RS-<A|T|D|H>-<slug>` (A: code or skill, T: tests, D: docs, H: needs the user or their machine), with its label, where it was found and how to reproduce it.

Labels: CONFIRMED (reproduced), INFERRED (read from code), HYPOTHESIZED, RULED OUT (checked and fine).

### Found outside the review rounds

- **exFAT copy** (CONFIRMED by another session on a 1 GB exFAT virtual disk, on 0.2.1; the 0.3.0 copy command was the same). The copy command failed every copy on exFAT with "is not the file this copy wrote": exFAT has no hard links (`linkSync` fails with `EISDIR`), so it renames the file into place, and a rename there changes the file's ID (393216 became 393344 in a probe: the ID follows the entry's place in its folder). The end check compared the target with the ID read before the move. Fixed in e58956b: the ID is read from the held handle after the move. Probed on exFAT and NTFS (`id-probe.cjs` in the session's scratchpad): on exFAT the handle's ID follows the file, so a file moved away and another renamed in still fails the check; an open file's name stays taken after unlink, so the unlink-and-replace swap can't be staged there; on NTFS the handle's ID never changes, so the check is the same as before. New tests: with a preload that makes `fs` act as on exFAT, a copy is accepted (fails on 91bb0d7) and the moved-away swap fails the copy (fails on a mutant that compares the target with itself). The suite on the exFAT drive, repo and `TEMP` both on it: 143 tests, 110 pass, 0 fail, 33 skipped; tests that need a hard link, a link to a folder or a freed name skip there (`tests/links.mjs`). With 91bb0d7's skills and the new tests on exFAT, 6 copy tests fail.

### Deferred

- **RS-A-stalerace** (INFERRED in round 1, low; the known race class). `look()` checks a file with `lstat` and `holds()` reads it by path, so a file swapped for a link or a second hard link between the two is read through it. `read()` has the same gap for the two log files; `--stale` widens it to up to 100 paths. Fix: open the file, compare `fstat` (inode, device, one link, a regular file) with the look, and read from the handle.
- **RS-D-stalesecrets** (HYPOTHESIZED in round 1, low). `--stale` searches any file in the repo, untracked ones too (`.env`, `.git/config`), so a planted entry learns one bit per name (whether the file holds the text), and only if the session then acts on the leads where an attacker sees it. SECURITY.md frames the risk as files outside the repo. Fix: name the limit in SECURITY.md, or search only files git tracks.
- **RS-D-staleleads** (round 1, docs). The CHANGELOG, the READMEs and step 6 say `--stale` lists files that are gone or no longer hold the text; it also lists `not checked` and `not searched` notes. This repo's own log gives 5 leads, all names that were never paths from the root (scratch files, paths inside a plugin folder).
- **RS-A-crstrip** (INFERRED in round 1). `holds()` drops `\r` from the file before searching, but search text can't hold a line break, so the strip changes no result, and a search can never match across lines, which no doc says.
- **RS-A-realpatherr** (HYPOTHESIZED in round 2, low). An error from `realpathSync.native` is reported as `no such file`. On a drive whose driver fails that call for files that exist, every name would read as gone, and a reader could close lessons that still hold. No such drive was found. Fix: `not checked: its real path can't be read`.
- **RS-T-growthguard** (INFERRED in round 2, low). The growth test refuses both inputs before any read on the fixed script, so there it times only Node's start. On 51c36f0 it fails with a margin of about 1.3 times on this machine (7185 ms against a limit of 5400), so a machine about 2.6 times faster would pass the slow script. Fix: drop the 1000 ms slack, or time 100 searches of 200 characters at the limit on 1 MB.
- **RS-C-casedir, widened** (INFERRED in round 2, from the code). The copy command's real-path check folds with `toLowerCase` too, so the Kelvin sign gets past it in an ordinary folder, not only in one marked case-sensitive. SECURITY.md's known limit now says so. The fix is the one `--stale` now uses: compare the repo's real path exactly and fold only ASCII case in the rest.

## 0.2.1

Base: 643dcdd (0.2.0 and its post-release records, on main). Closes RS-A-claudewrite and RS-A-fromlabel.

- The copy command in both skills writes the template under a random name beside the target and gives it the target's name with a hard link (`linkSync`), which fails on anything at that name (`EEXIST`) and follows no link. On any other link error it renames the file into place, which writes through no link but replaces a plain file made at the name in that instant. Codex's Windows sandbox refuses the hard link (`EPERM`), so Codex uses the rename. A probe showed why the 0.2.0 create-only write wasn't enough: on Windows it follows a dangling file link and makes an empty folder through a dangling junction. The command also refuses a source or folder that is a link, a source with a second name, and a source or folder that changes between the look and the read (inode and device compared, the source and its folder looked at again after the read), a target folder that is not a folder, and names any random-name file it can't remove. Last, it checks that the target is the very file it wrote (the inode of the handle it wrote through, one name). The Claude Code skill writes templates into a random staging folder (`mkdtempSync`) and uses the same command.
- `--check` keeps only the 50 messages it prints, and makes none for a bad `From:` name past them. On 465,000 bad `From:` names, the old script needs 256 MB of heap and the new one 40 MB on Node 26 (128 MB on Node 18, where the old one also needs 256 MB).

Fail-before runs: the heap test (192 MB since round 11; it was 96 MB, too little for the new script on Node 18) fails on the 0.2.0 script (out of memory) and passes on the new one. On the 0.2.0 skills, 13 of the new copy tests fail, among them the dangling junction made after the check (an empty folder appeared where it pointed). One of them, the file made at the target after the look, fails there only on its message: 0.2.0 kept the file. It guards round 1's rename-only command, which replaced it. Two pass on both: the one-name test and the rename fallback, which guard the new design. Tests added for a mutant rather than a fix were each run on that mutant and failed there. The laziness test fails on the 0.2.0 script and on a mutant that builds every message and drops it. The dangling file-link test, run elevated, passed on both the old and the new command, against a direct probe in which the create-only write wrote through such a link: RS-H-oldrace.
